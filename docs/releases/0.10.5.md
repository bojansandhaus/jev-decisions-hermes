# Jev Decisions 0.10.5

0.10.0 fixed four ways the approval boundary failed open and named six more
issues it did not touch. This release is those six. All of them share one
property with the four before: a bound, a sample, or a fallback silently chose
the permissive reading, and the caller had no way to know.

`docs/releases/0.10.0.md` recorded these as the next candidates. Each is now
closed and pinned by `tests/test_known_issues_regressions.py`.

| | v0.10.0 | v0.10.5 |
| --- | --- | --- |
| test suite | 535 passed, 4 skipped | **562 passed, 4 skipped** |

---

## The decision journal was forgeable by the party it judges

The ledger is append-only JSONL with no hash chain, signature, or writer
identity, so any process with write access can append or truncate it. That is
recorded below as still open. What was *also* true, and is not, is that the
reviewed agent held the pen on its own grading.

`record_outcome` wrote no record of who claimed the outcome, and the one path
that did record one read the name out of the tool arguments:

```python
result = loop_label_outcome(
    args["decision_id"], args["success"], args.get("evidence"),
    args.get("labeler", "user"),        # <-- caller-supplied
    args.get("notes", ""),
)
```

So the agent could label its own review `correct: true` and sign the label as
the operator's, in the same call. Those rows drove `metrics()`, which counted a
self-certified correctness exactly like a human check, and the shadow report
read them as the operator's judgement.

**What changed.** `labeler` is now set by the code path, never by the caller's
arguments. Every label arriving through a registered tool is signed
`AGENT_LABELER`; operator code that calls `record_outcome` or `label_outcome`
directly leaves the default of `"user"`. `closed_loop.record_outcome` and
`gateway.record_outcome` both record it now, where neither did before.

`shadow_report.closed_loop_calibration` reports agent labels beside the operator
figure rather than folding them into it. A shadow report that grades itself on
its own labels can no longer report perfect accuracy while being wrong:

```
rows: 3x agent-labelled (2 correct, 1 wrong), 2x operator-labelled (1 each)
  labeled 2   correct 1   accuracy 0.5     # was labeled 5, accuracy 0.6
```

**Still open.** The append-only store itself has no hash chain, so truncation
remains undetectable and an external writer can still append. Detecting that
needs each record to carry the previous record's id, which changes the on-disk
format — a major-release change, not a patch. The `labeler` above closes the
attack that needed no filesystem access at all.

## Turn eviction dropped a live blocking control

`begin_turn` evicted the oldest tracked turn with `next(iter(self._turns))`,
whatever it held:

```python
if len(self._turns) > self._config.max_tracked_turns:
    oldest = next(iter(self._turns))
    dropped = self._turns.pop(oldest)
```

A turn still live lost its active control, and `check_control` then reported
`allow: True` for the exact action that control was blocking — because a turn
that cannot be resolved is indistinguishable from a turn with nothing to
enforce. In `precommit` that is a fail-open of the one thing enforcement does,
reachable by ordinary unrelated traffic. Verified:

```
begin T1(s1), T2(s1), T3, T4  -> _session_turn == {}
resolve by session s1: None
control after overflow: {'controlled': False, 'allow': True}
```

**What changed.** A blocking control is never evicted. The oldest turn *without*
one is dropped instead. The turn currently being started is excluded from the
candidates — without that, the newest turn is always the first control-free one
in insertion order, so it would be evicted every time and no turn created after
the cap could ever accumulate a control.

If every tracked turn holds a control, the map grows past `max_tracked_turns`.
That is deliberate and it is bounded: a `ControlDirective` carries no expiry and
a turn is freed only by `end_turn`, so the refusal to evict would otherwise be a
leak in a process where turns never end. `control_retention_limit` (default 256,
env `JEV_SUPERVISION_CONTROL_RETENTION`) is the hard ceiling where the memory
bound wins — and the loss is no longer silent. It is counted as
`controls_evicted` and appended to the ledger, so an operator can see that a
blocking control was dropped and why.

```
max_tracked_turns=2, six turns all blocked:
  tracked 6, evicted 0, retained_past_cap 4, controls_evicted 0, blocked 6/6
control_retention_limit=4, ten turns all blocked:
  tracked 4, controls_evicted 4        # bounded, and the loss is observable
```

`no_turn` also names itself now. A bare `allow: True` could not be told apart
from "nothing to enforce":

```python
{"controlled": False, "allow": True, "mode": "precommit", "reason": "no_turn"}
```

## `metrics()` reported a 5,000-row sample as totals

The comment on the cache said `metrics()` "is a pure function of the store's
contents". It is a pure function of the last 5,000 rows, and the stores have no
size cap, so on a taller store the numbers were sample statistics presented as
totals. Reproduced on an 8,000-row store:

| metric | reported | truth |
| --- | --- | --- |
| `reviews` | 3,500 | 5,000 |
| `outcomes` | 1,500 | 3,000 |
| `labeled_reviews` | 1,500 | 3,000 |

`unlabeled_reviews` happened to stay right, and for a reason worth recording: a
review is appended before its own outcome, so every review inside a window
carries its outcome inside the same window. The window is only ever short of the
rows that scrolled out, never short of a pairing.

**What changed.** `sampled` and `window_rows` say so. The counts are unchanged
and the performance is unchanged; what changed is that an operator can now tell
a total from a window, which is the part that was false.

```
8000-row store: reviews 3500, window_rows 5000, sampled True
10-row store:   reviews 10,   window_rows 10,   sampled False
```

The incorrect comment is corrected rather than worked around.

## `tail_lines()` dropped a row at exact block boundaries

`tail_lines` walks backwards in 64 KB blocks and drops the first line of the
result on the assumption that it is a fragment of a record that began earlier.
When `limit` rows happened to fill a whole number of blocks, that first line was
complete and was dropped anyway. Verified on 9,000 lines of 8 bytes:

```
limit=8191: n=8191 exact=True
limit=8192: n=8191 exact=False   <-- one row lost
limit=8193: n=8193 exact=True
```

`read(8192)`, `closed_loop.list_records`, and `fabric.queue` are all downstream.
`test_store_read_bounds.py` asserts read *bounds*, never the row count against
the limit, so no existing case landed on the boundary.

**What changed.** The walk asks the byte one before the read whether it is a
newline, instead of assuming it is not. Exact across every limit from 1 to 9,000
on that file, and a read that genuinely starts mid-record still loses its
partial first line.

## `ingest` leaked a slot per unverified result, and closed the wrong case

Both tracking maps were cleaned only inside `if verified:`:

```python
if verified:
    if invocation_id:
        _ACTIVE_INVOCATIONS.pop(str(invocation_id), None)
    ...
```

`verify_observation` returns `verified: False` for any result without an
`expected` field, which is the common case for a tool call, and
`_on_post_tool_call` passes that value straight in. So every hooked tool result
leaked one dict entry and one case row for the life of the process.

A second defect in the same function: when `invocation_id` was absent or unknown,
lookup fell through to `pending[0]`, closing the *oldest* open case for that tool
name. The wrong case got `resolved` while the real one stayed open.

**What changed.** Every outcome is terminal for a case, so every outcome frees
the slot. An invocation id that is present but unknown is an unknown case and
returns `None` rather than resolving someone else's. The maps are bounded at 512
as a last line behind that fix, not a substitute for it.

```
5 unverified results: cases 0, invocations 0
unknown invocation id -> None; the real case still tracked
700 opens, no results: cases 512 (<=512), invocations 512 (<=512)
```

## `_boolean` fail-opened on any non-boolean value

```python
def _boolean(state, key, default):
    value = state.get(key, default)
    return value if isinstance(value, bool) else default
```

Every policy flag defaults toward "no human needed", so a flag that was present
but not a boolean was read as the safe case:

```
{'external': 1}              -> decision 'observe'   # an action reaching the network
{'credential': 'yes'}        -> decision 'observe'
{'reversible': 0}            -> decision 'observe'
{'external': 1, 'reversible': 'no'} -> decision 'observe'
```

`tests/test_gateway.py` pinned the string case and passed, because `"false"`
happened to be conservative.

**What changed.** A flag that is present and is not a boolean makes the state
unreadable, and an unreadable state is refused rather than coerced:

```python
{"external": 1} -> {"decision": "invalid_state", "authority": "invalid_state",
                    "reason": {"malformed_flags": ["external"]}}
```

The test that pinned the coercion is rewritten to pin the refusal, and its
replacement records why the old assertion was wrong rather than quietly
replacing it. Absence still uses the default, and a real boolean still routes —
without that, the refusal would become an anything-goes gate.

## What is still open

- **The ledger has no hash chain.** Truncation is undetectable and an external
  writer can append. Detecting it changes the on-disk format and belongs in a
  major release.
- **The T0–T4 history ladder can shrink history so far that candidates are ranked
  against evidence no longer in the state**, with no flag saying so. Found in
  `jevs-lcm-*` and recorded there; the same shape exists in this repo's
  `state_shaper` equivalents if any are added.
- **`metrics()`'s window is 5,000 rows.** A store taller than that still reports
  a window, now declared. Making it complete would defeat the cache.
- **`_boolean`'s new `invalid_state` decision** is a new value in the
  deterministic-policy surface. Callers that switch on `decision` without a
  default will need one; nothing in this repo does.
