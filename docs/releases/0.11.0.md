## The decision journal is now hash-chained

0.10.0 and 0.10.5 both recorded this as the one structural item left. The ledger
is append-only JSONL with no hash chain, signature, or writer identity, so any
process with write access to `$JEV_HOME/logs/` could append or truncate it. The
`labeler` fix in 0.10.5 closed the attack that needed *no* filesystem access at
all; this closes the one that does.

Each record now carries `prev_id` and `chain_hash`. The hash covers the previous
link as well as this record's own body:

```python
def _link(prev_hash: str, payload: dict) -> str:
    return hashlib.sha256(f"{prev_hash}|{_canonical(payload)}".encode("utf-8")).hexdigest()
```

Covering the previous link is what makes both attacks detectable. Hashing only
the id would have caught truncation and missed rewriting: an edited record keeps
its id, so an id-only chain would still verify. Verified against both:

```
truncating a record  -> chain_hash_mismatch, at <record id>
rewriting a body     -> chain_hash_mismatch, at <record id>
```

`chain_hash_mismatch` is reported for both, because both end with a record whose
declared hash disagrees with the body it was computed from. In the truncation
case the survivor's hash was computed over a `prev_hash` that no longer exists;
in the rewrite case the body changed under a hash that stayed.

A break reports **where the walk stopped**, as a record id, so it is findable by
eye rather than being a boolean that says "somewhere".

### The chain is additive, and that is deliberate

A record written before this change carries no `chain_hash`, links to nothing, and
is reported as an `unlinked_head` rather than as a break:

```
3 pre-chain records             -> intact True,  unlinked_head True,  linked 0
3 pre-chain + 3 chained records -> intact True,  unlinked_head False, linked 3
```

A ledger that predates the feature has not been tampered with — it is older — and
a format that accused every existing ledger on first run would be a format nobody
could adopt.

**A defect the test caught while writing this.** The first chained record of an
existing ledger legitimately points at the last pre-chain one, but the walk only
tracked chained ids, so that ordinary transition read as a missing link. Fixed by
tracking every record's id; the mixed case is pinned by a test that failed before
the fix.

`verify_chain` is an **operator** action on `jev_ledger`, not an agent-facing one.
It is declared in the tool schema and documented in `docs/reference.md`, and it
reports the full shape it produced.

### What this does and does not do

It makes truncation and rewriting **detectable**. It does not make the ledger
appendable-to by nobody: a process with write access can still write, and a
determined attacker can rewrite the whole file and recompute every link. What it
removes is the cheap, silent kind of tampering — the record dropped from the
middle, the `correct: true` edited in afterwards — because those now leave a
chain that does not verify, and say which record stopped it.

### Cost

One backward-seek to the tail per append, under the flock `tail_lines` already
uses:

```
2000 appends with chaining: 0.244 ms per append
```

## A lesson-guard failure now reaches the operator

0.10.5 recorded this as Low. `_lesson_gate` swallows every exception it raises,
which is correct — a `pre_tool_call` callback that raises is resolved as a BLOCK
on the user's tool call, so an escaping exception would veto the tool rather than
pass it. But it kept the failure in two process-local counters, and the only way
to read them was `jev_lessons action=stats`, a tool **the agent being gated
calls, and the same agent that can ignore what it says**.

So a store that had been unreadable for days was invisible to everyone but the
party whose behaviour it was supposed to be constraining.

**What changed.** The first failure per process is appended to the ledger as
`lesson_gate_error`, which an operator reads regardless of what the agent does.
Later failures bump the counter only:

```json
{"kind": "lesson_gate_error", "error_type": "OSError", "detail": "...", "tool_name": "terminal"}
```

Appending per failure would let a broken store grow the ledger without bound,
which is its own denial of service — the counter already tells you how often it
happened, and the first record tells you it did.

Reporting the failure cannot itself become the failure: the append is wrapped, so
if the ledger is what is broken the gate still abstains and still returns. That
is pinned by a test in which the ledger write raises.
