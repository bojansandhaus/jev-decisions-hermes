# Jev Decisions 0.9.0

## The `limit` argument on every store read was decorative

`ledger.read(limit)` did `path.read_text().splitlines()[-limit:]`. The slice
bounded what was **returned**, never what was **read**, decoded and split, so
asking for 10 rows cost the same as asking for 5,000. `closed_loop._read()` was
worse: no limit at all, every call.

The stores are append-only with no size cap, so this was not a constant-factor
cost. Every `metrics()`, every `queue()`, every `digest()`, and every
`jev_ledger action=list` paid O(total history) forever.

Measured on a 3.8 MB, 52,500-row store:

| operation | v0.8.0 | v0.9.0 |
| --- | --- | --- |
| `read(10)` | 11.31 ms | **0.33 ms** |
| `read(200)` | 10.74 ms | **0.92 ms** |
| `read(5000)` | 18.03 ms | 19.19 ms |

`read(10)` used to cost 96% of `read(5000)`. It now costs about 1.7%. A
50,000-row store is a plausible year of history for a busy agent; at that size
the old path spent a third of a second per digest.

`tail_lines()` walks backwards in 64 KB blocks and stops once it has seen
`limit` newlines. A file smaller than one block is read whole. Verified
byte-identical to the old implementation across every window tested, including
a 40,000-row file where the first line is a mid-record fragment and must be
dropped rather than parsed.

## `metrics()` is now cached on (mtime_ns, size)

`metrics()` is a pure function of an append-only file, and `digest()` calls it
along with `queue()`, while the gateway's `snapshot()` calls it directly. Since
the store only grows by appending, `(mtime_ns, size)` identifies its contents
exactly, so a repeat call costs one `stat`.

```
cold 17.46 ms   warm 0.004 ms   4,366x   values identical
```

`append()` drops the cache explicitly, so invalidation does not depend on
filesystem mtime resolution, and a write by another process is still observed
because the key is derived from `stat` rather than from a call.

## Also fixed

- `closed_loop.list_records()` capped its **result** at 500 while reading the
  whole file. It now reads only as far back as it returns.
- The by-`decision_id` lookup still reads whole-file. That is correct: it can
  match any row, so it cannot be bounded the same way.

## Not changed, deliberately

Two structural costs remain, both real and both needing a design decision rather
than a patch:

- **Seven fsync'd appends per tool call** with hooks enabled, four of them
  carrying information derivable from the others. `ledger.append_many()` writing
  N lines under one flock and one fsync is the fix, but it changes the on-disk
  shape and wants its own change with its own tests.
- **The lesson store's read cache never re-reads.** A long-lived process misses
  rules written by the CLI, cron, or another session for its whole lifetime. It
  is also not buying measurable speed, so the fix is to key `_load()` on
  `(mtime_ns, size)`. This one is small and is the recommended next change.

## An infrastructure state is not an error report

`verify_observation` opened with:

```python
if text.startswith("collector_error:") or "error" in text or "timeout" in text:
```

`text` is the whole result, lowercased and stringified. For a dict result that
is `"{'state': 'errored'}"`, so the word `error` inside the STATE matched and the
observation was reported `unavailable`.

That is not a rare spelling. `errored`, `error_free`, `no_error`, and
`timeout_reached` are ordinary state names for the systems this plugin watches,
and all four were misreported. The call sits in `_on_post_tool_call`, so it runs
on **every** hooked tool result, and a misreport writes `awaiting_verification`
into the closed loop for a result the host had actually verified. The
consequences point the wrong way: a good result looks unverified, and the review
queue fills with noise that was never a failure.

The comparator now looks for a signal rather than a word:

| result | before | after |
| --- | --- | --- |
| `{"state": "errored"}`, expected `errored` | `unavailable` | `matched` |
| `{"state": "error_free"}`, expected `error_free` | `unavailable` | `matched` |
| `{"state": "no_error"}`, expected `no_error` | `unavailable` | `matched` |
| `{"state": "timeout_reached"}`, expected `timeout_reached` | `unavailable` | `matched` |
| `{"state": "online", "note": "no_error since reboot"}` | `unavailable` | `matched` |
| `"collector_error: dial tcp: refused"` | `unavailable` | `unavailable` |
| `{"state": "running", "error": "boom"}` | `unavailable` | `unavailable` |
| `{"state": "ok", "error": None}` | `unavailable` | `matched` |
| `"request timeout after 30s"` | `unavailable` | `unavailable` |

A dict is inspected for an `error`, `errors`, `timeout`, or `timed_out` KEY and
never for those words inside a value. A key that is present but empty
(`{"error": None}`, `{"error": ""}`) is not a failure, because the producer
reported that there is nothing to report; reading that as a failure is the same
mistake in the other direction. A bare string has no structure and no keys, so
its whole content is still the signal, and the documented contract for the string
case is unchanged.

## The supervision schema forbade what its own handler accepted

`configure` accepted seven fields:

```python
settable = {"enabled", "mode", "admission_enabled", "relevance_threshold",
            "challenge_confidence", "max_provider_calls_per_turn",
            "repeated_failure_replan_at"}
```

`JEV_SUPERVISION_SCHEMA` declared `additionalProperties: False` and listed only
`mode`. Six of the seven were rejected at the tool boundary while the handler
returned `success: true` for them when called directly. Through the tool, the
action could switch a mode and nothing else.

The existing test passed because it called the handler function directly and so
bypassed schema validation entirely. It now checks both sides: every key in the
settable set must be present in the schema's properties, each declared type must
match what `configure` coerces to, and each field must validate against the real
schema before the handler runs. The drift is now impossible to reintroduce
quietly, because the set is one `JEV_SUPERVISION_SETTABLE` tuple read by both
the handler and the test.

The handler was **not** trimmed to match the schema. Those six fields are working
behaviour that a user could already reach through a Python caller, and deleting
them would have removed it.

## `assess()` was missed when `list_records` was bounded

`assess()` called `_read()` with no limit at all, so every call decoded the whole
store into one string and then a list of one string per row, and ran `json.loads`
on every row, to answer a question about a single decision. It is reachable from
`jev_loop action=assess`.

**It cannot be given a bounded tail**, which is the fix `list_records` got. A
decision recorded before the window is a decision that exists; a tail read would
report `found: False` for it. On the 60,120-row store used to measure this, the
decision under test occupied rows 0 through 119 and a 5,000-row tail did not reach
it. The docstring already warns about this: a decision is reported missing rather
than merely absent from the window.

So the bound is on the work rather than on the bytes read. The store is walked in
blocks, each line is a cheap byte-level substring test, and only a line naming
the decision is parsed:

| | 6.2 MB, 60,120-row store |
| --- | --- |
| `assess("d1")` before | 148.8 ms |
| `assess("d1")` after | 21.5 ms |
| `list_records(10)`, for scale | 0.22 ms |

The substring test is a filter, not a definition, and it is worth being exact
about its one blind spot: an ID written with non-ASCII text is stored escaped, as
`json.dumps("uni-\u00e9\u4e2d")` writes `uni-\u00e9\u4e2d`, so the ID cannot
match its own bytes.
Rather than report such a decision missing, an empty prefiltered result falls back
to the exact whole-store scan. Every ID this module generates is a hex `uuid4`
and matches literally, so the fallback is off the hot path; it exists so the
optimization cannot change an answer. A miss on a store that genuinely has no
such decision still costs a full scan, which is the price of never lying.

Output is unchanged, and asserted to be: `tests/test_store_read_bounds.py`
compares `_read_matching` against a whole-store scan over randomized rows, and
repeats the comparison with a 64-byte block size so most records straddle a read.

## Two bare imports named the wrong module in package mode

Every module here imports siblings through the same pair, so a host may load
them flat from the checkout root or as package members:

```python
try:
    from .ledger import tail_lines
except ImportError:
    from ledger import tail_lines
```

`closed_loop.py` and `approval_review.py` each placed their sibling import ABOVE
that `try`, flat and unconditional. A host importing the directory as a package
has no checkout root on `sys.path`, so both raised `ModuleNotFoundError` naming a
module that exists one directory up, which is the misleading error the `try`
exists to prevent. Measured by copying the repository into a package and
importing it with only the parent on the path:

```
before:  closed_loop       -> ModuleNotFoundError: No module named 'ledger'
         approval_review   -> ModuleNotFoundError: No module named 'approval_policy'
after:   both import cleanly
```

## Version and CHANGELOG hygiene

`pyproject.toml` said `0.9.0` and `plugin.yaml` said `0.8.0`. Hermes reads
`plugin.yaml`, packaging reads `pyproject.toml`, so the published manifest
advertised a version that did not exist in the package. Both say `0.9.0` now.

`RELEASE_NOTES_v0.9.0.md` sat at the repository root while `docs/releases/`
ended at `0.8.0.md`, and the 0.9.0 CHANGELOG entry was appended below 0.1.0
under `## 0.9.0 - 2026-10-05`, where every other entry uses `## [version] - date`
and descends from newest. The note moved to `docs/releases/0.9.0.md` and the
entry moved to the top in the established style, so the claim at `CHANGELOG.md:5`
that the release notes are the canonical record is true again.

the fixes reverted, because the whole-file read of a 20,000-row store measures
1.8 ms, which clears any threshold loose enough to be stable on a loaded CI
runner. The bounds tests now count the bytes actually read off disk, and the
`assess` test counts `json.loads` calls, which asserts the mechanism instead of
the speed.
