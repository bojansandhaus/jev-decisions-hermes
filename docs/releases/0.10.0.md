# Jev Decisions 0.10.0

Four ways the approval boundary used to fail open. Each one is the same shape:
evidence that was missing, ambiguous, or supplied by the party being judged was
read as a reason to permit. None of them were reachable from the happy path,
which is why a suite of 506 passing tests contained all four.

The release notes for 0.9.0 describe a store-read optimisation and a schema
drift fix. This one is different in kind: every change below tightens a
decision, and each is pinned by a regression test that fails on the previous
version.

| | v0.9.0 | v0.10.0 |
| --- | --- | --- |
| test suite | 506 passed, 4 skipped | **535 passed, 4 skipped** |

---

## A model refusal was upgraded to an approval by operator policy

`approval_policy.apply_policy()` applied host rules after the model's typed
answers were validated. The rule read:

```python
if policy >= 0.7 and has_policy and blast < 2.0:
    raw = "APPROVE"
    reason = "trusted operator policy matched"
```

`raw` at that point was still the model's verdict, and nothing restricted the
upgrade to a model that had approved or escalated. A DENY was overwritten as
freely as an ESCALATE.

The confidence and blast-radius guard two lines below could not rescue it,
because it tests the *model's confidence in its own DENY* — which is exactly
when the model is most sure of the refusal. Verified against the real function:

```
verdict DENY, confidence 0.99, policy_allows 0.71, blast 1.2
  -> ApprovalDecision(verdict='APPROVE', rule='trusted operator policy matched')
```

`has_policy` requires only that *some* policy text was supplied, and
`policy_allows` is one model probability on an ungrounded question. So a config
carrying a vague sentence — "we do routine dev work on this box" — plus
`policy_allows >= 0.7` turned a `DROP DATABASE prod`-class DENY into an
APPROVE. The upgrade was driven by weaker evidence than the refusal it
overrode.

The same rule exists twice. `integrations/approval-provider/__init__.py` is the
copy that actually ships, and it had diverged in nothing meaningful, but it is
maintained separately. Both are fixed together, and a new regression test runs
the shipped provider path on the same input and asserts it refuses too.

**What changed.** An operator policy resolves an ESCALATE or confirms an
APPROVE — that is the owner's own written statement about what kind of work
happens here, and it is the right thing to resolve uncertainty with. It no
longer resolves a DENY. A refusal the model was itself unsure about goes to a
human, which is what every other uncertain path in the module already did and
what `tests/test_hardening.py:188` had been asserting all along.

That last detail is the reason this survived: the existing test passed for the
wrong reason. It asserted ESCALATE, and got ESCALATE — but only because the
DENY had been rewritten to APPROVE and then downgraded again by the confidence
guard. The assertion never examined the verdict the model actually gave.

```
model DENY      conf 0.99 + policy 0.71 -> DENY       (was APPROVE)
model DENY      conf 0.54 + policy 0.71 -> ESCALATE   (was APPROVE, then downgraded)
model ESCALATE  conf 0.99 + policy 0.71 -> APPROVE    (unchanged: the intended upgrade)
model APPROVE   conf 0.99 + policy 0.71 -> APPROVE    (unchanged)
```

## The supervised agent could weaken its own owner rule

An owner rule is the hardest thing the lesson store can hold. `retire()`
refuses one (`lessons.py:641`) and `sweep()` refuses one (`lessons.py:654`),
and the README states the promise: an owner rule "is a hard stop from the
moment you make it, and it can never retire."

`edit()` had no such check:

```python
if severity is not None:
    item.severity = severity if severity in SEVERITIES else item.severity
```

`edit` also rewrites `text`, `scope`, `detect`, and zeroes the escape and catch
counters. `local_kicks()` returns only `severity == "kick"`, so one call lowered
a hard stop to a nudge and the gate simply stopped firing. Verified end to end,
including the hook path:

```
1) gate blocks: True
   after edit severity: nudge   (source: owner)
   gate blocks now: False
```

`text` was rewritable too, so the rule's wording could be edited away from the
mistake it was written for.

The trust boundary is the problem, not the guard. `jev_lessons action=edit` is
a tool the agent being gated calls, so the party being judged held the keys to
its own lesson store.

**What changed.** An owner rule is now exempt from `edit` wholly rather than
field by field — severity, text, scope, detect, escapes, catches, all refused,
with a new regression test parametrised over every one of those fields. There is
deliberately no operator exception, because this method is the model-facing
boundary and an authority flag the model cannot pass is the only one that
cannot be forged.

Non-owner lessons remain fully editable; that is the path that legitimately
undoes a wrong escalation, and `tests/test_lessons.py:195` still passes
unchanged.

## One tool call turned supervision off

`jev_supervision action=configure` accepted `enabled` and `mode`. Both were in
`JEV_SUPERVISION_SETTABLE`, and `jev_supervision` is a registered tool the
model calls. There is no distinction in the code between an operator driving
this tool and the agent whose actions are being gated.

Once `configure` returned, `enforcing()` was False and `check_control()`
returned `allow: not enforcing`, so the very next `pre_tool_call` on the same
action ran. Verified end to end:

```
enforcing: True
1) gate blocks: True
2) agent sets mode=shadow -> shadow
   enforcing: False
   gate blocks now: False
```

This is the second time this repo has had a `jev_supervision` boundary defect.
0.9.0 fixed the schema forbidding six fields its handler accepted; the note for
that release records that "a caller crossing the tool boundary could change
`mode` and nothing else." The handler was widened, and in widening it the
enforcement switch itself was left reachable.

**What changed.** `enabled` and `mode` are no longer settable through the
model-facing tool.

`enabled` is removed from `JEV_SUPERVISION_SCHEMA` as well, so the tool
boundary rejects it before the handler is reached — nothing but `configure`
ever took it, so this is a second line of defence at the real boundary rather
than a filter inside it. `mode` has to stay declared, because the read-only
actions (`status`, `check_control`) take it, so it is refused by the handler
instead.

The refusal is explicit rather than silent. A filtered-out field would look
like success; the handler now names what it refused. Operator code and the test
suite still set `mode` and `enabled` by calling `Supervision.configure()`
directly, where the caller is the process that owns the policy rather than the
agent it polices, and a new test pins that this still works.

```
{"action":"configure","mode":"shadow"}
  -> error: enforcement cannot be changed from the supervised tool boundary (mode is operator-only)
enforcing still: True | mode still: precommit
```

## A timeout consumed the control that was blocking a failing action

`record_tool_outcome()` classified a result by looking for a failure
signature. If it found none, it recorded success, and a success consumed an
active REPLAN control:

```python
if not error:
    if turn.active_control is not None and turn.active_control.action_fingerprint == action_fp:
        turn.active_control.consumed = True
```

`normalize_error()` recognised only `error`, `success is False`, and `ok is
False`. A result shaped `{"timeout": 30}`, `{"timed_out": true}`,
`{"errors": ["boom"]}`, or the string `"timeout: command timed out"` rendered
**no failure signature at all**, so it was recorded as a success and the
control that was blocking the exact failing action was released.

In `precommit` mode this is a direct fail-open of the one thing enforcement
does. Verified against the real `Supervision`:

```
control created: REPLAN count 3
blocked? {'controlled': True, 'allow': False, ...}
timeout result -> {'recorded': True, 'outcome': 'success', ...}
control after a timeout for the same action: {'controlled': False, 'allow': True, ...}
```

The failure-episode count was cleared too, so the action could keep failing
forever without the threshold ever being reached again.

`verification.py` already knew the right key set — `_ERROR_KEYS` is
`{"error", "errors", "timeout", "timed_out"}` — and `normalize_error` did not
consult it. The two modules that read tool results had drifted apart.

**What changed, in two parts.**

*The key set is shared, not duplicated.* `normalize_error` now reads the same
four keys with the same "present but empty is not a failure" rule, and the two
sets are asserted equal by a new test so the next addition to one fails there
instead of silently failing open in production.

*Absence of a failure is no longer success.* This is the part that matters. A
new `_succeeded()` requires positive evidence that a call completed: an
affirmative marker, a result carrying no keys at all (the ordinary "ran and had
nothing to report" shape), or a bare string with content and no signal in it.
A dict whose status cannot be read is reported as `outcome: "unknown"` and
consumes nothing.

```
{'timeout': 30}                failure sig '30'                 positive: no
{'timed_out': True}            failure sig 'true'               positive: no
{'errors': ['boom']}           failure sig "['boom']"           positive: no
timeout: command timed out     failure sig 'timeout: ...'       positive: no
{'status': 'running'}          no signature                     positive: no
{'success': True, ...}         no signature                     positive: YES
{}                             no signature                     positive: yes (no output)
'all good'                     no signature                     positive: YES
```

A confirmed success still consumes the control. Without that, enforcement
would deadlock on the first transient failure that later healed, and
`test_success_clears_the_failure_episode` still passes unchanged.

## What this release does not fix

Recorded here rather than left to be rediscovered, because these are the paths
a reader of the four fixes above will reasonably expect to be closed and are
not:

- **The decision journal is forgeable by the party it judges.** The ledger is
  append-only JSONL with no hash chain, signature, or writer identity.
  `record_outcome` lets the reviewed agent label its own review
  `correct: true`, and spamming `jev_lessons action=surfaced` auto-retires a
  learned kick lesson through `sweep()`. Neither fix above touches this.
- **Turn eviction drops a live session's blocking control.** `no_turn` under an
  enforcing mode reports `allow: True`, so eviction converts a blocking control
  into a permission. `max_tracked_turns` is reached by ordinary traffic.
- **`metrics()` reports on a 5,000-row sample** while its comment claims to be
  a pure function of the store's contents, and `promotion_ready` reads off it.
- **`tail_lines()` drops one row at exact block boundaries** — `read(8192)`
  returns 8,191 rows on a file whose block boundary lands on 8192.
- **`ingest`'s module-level case maps grow without bound,** and an unknown
  `invocation_id` closes the *oldest* open case for that tool name.
- **`_boolean` fail-opens on any non-boolean value.** `{"external": 1}` reads as
  not external.

`tests/test_fail_closed_regressions.py` is the new home for the invariant this
release is about — *when the evidence is missing, ambiguous, or supplied by the
party being judged, the answer is never the permissive one.* The items above
are the next candidates for it.
