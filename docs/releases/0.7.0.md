# Jev Decisions 0.7.0

This release adds Cloudflare Clef as a third hosted decision provider, beside Jev over TypeSafe and OpenRouter and beside Laya locally. It is purely additive: every existing provider mode, every existing alias, and every existing test behaves exactly as it did in 0.6.1, and the default is still `openrouter`. What is new is one provider name, one checkpoint setting, two Cloudflare environment variables, and the `clef_api` DOGA alias.

## Added

### The Clef provider

`JEV_PROVIDER_MODE=clef` sends the bounded review state and the typed questions to Cloudflare Workers AI:

```
POST https://api.cloudflare.com/client/v4/accounts/<CLOUDFLARE_ACCOUNT_ID>/ai/run/@cf/cloudflare/clef
{"model": "clef", "state": <state>, "questions": <questions>}
```

Clef is a **provider, not a chain member**. It has exactly one name, it is never appended to a mode that does not name it, and it has **no fallback at all**: a Clef failure is a failure of this route, raised, never a licence to quietly call a second classifier. There is no `clef_then_*` mode and no `laya_then_clef` mode, and `provider_order("clef")` is exactly `("clef",)`.

### Two credentials, two kinds of value

| Variable | Kind | Requirement |
|---|---|---|
| `CLOUDFLARE_API_TOKEN` | credential | a Cloudflare API token with **Account > Workers AI > Read**, sent as a bearer token in the `Authorization` header |
| `CLOUDFLARE_ACCOUNT_ID` | configuration | the 32 character account id the run endpoint is scoped to |

Both are checked **before any socket is opened**, and a missing one raises naming the variable. Both missing names are reported together, so a first run needs one fix rather than two. The account id is configuration rather than a secret, but it is interpolated into a URL, so it is validated as exactly 32 lowercase hex characters: a value carrying `../` or a slash would rewrite which endpoint the request reaches, and is refused before anything is sent. A test asserts a `../../other-account` account id raises with no request attempted.

### The checkpoint is a setting, not a provider

`clef` and `clef-flash` are two checkpoints of the one provider, chosen with `JEV_CLEF_MODEL`, which defaults to `clef`. `clef-flash` is **rejected if you set it as `JEV_PROVIDER_MODE`**, because a mode name is a route and a checkpoint is not. An unrecognised `JEV_CLEF_MODEL` fails naming the accepted values rather than calling a checkpoint that does not exist. The checkpoint appears in both the endpoint path and the body's `model` field, and a test asserts `clef-flash` routes to `/ai/run/@cf/cloudflare/clef-flash` with `"model": "clef-flash"`.

### The `clef_api` alias

The DOGA fork names four arrangements; this release adds the third accepted alias. `MODE_ALIASES` now maps:

| DOGA name | Resolves to | Providers tried, in order |
|---|---|---|
| `clef_api` | `clef` | `clef` |
| `laya_local` | `laya` | `laya` |
| `laya_with_jev_fallback` | `laya_then_openrouter_typesafe` | `laya`, `openrouter`, then `typesafe` |

`clef_api` selects Clef alone with no fallback, deliberately. The canonical mode count is now ten and the alias count three, so `JEV_PROVIDER_MODE` accepts thirteen values; anything else is still rejected with an error listing the whole accepted set.

### Both response envelopes

Cloudflare serves the model output directly from the run endpoint as `{"model", "answers", "usage"}`, and its general REST surface wraps that in `{"success": true, "result": {...}}`. The route **prefers a top-level `answers` and falls back to `result.answers`**, and a test asserts the preference when a response carries both with different values. A `{"success": false}` envelope is refused with **Cloudflare's own error codes** in the message, since those identify what went wrong where a generic parse failure would not. Several codes are all surfaced.

### Question ids are mapped, and mapped back

This is the load-bearing part. Clef accepts letters, digits, `_`, `.` and `-` in a question id, up to 100 characters, and this repository builds ids whose colon Clef refuses, such as `candidate:aaa` and `hook:name`.

- A colon becomes an underscore: `candidate:aaa` is sent as `candidate_aaa`, so a wire capture stays legible.
- An id Clef already accepts is sent **untouched**, so a caller whose own ids are all Clef-legal never sees a rename.
- An id too long to send is truncated and gains a short digest of the original, so truncation cannot make two questions collide.
- Two caller ids that would land on one Clef id are disambiguated rather than silently merged.
- Every answer is mapped back to the caller's own id, so `request_decisions` returns `{"candidate:aaa": ...}`, never the substituted name.

A request with **more than 64 questions** is refused before it is sent. That limit is Clef's, and a test proves it applies only to the route that names it: 70 questions still go through `typesafe` unchanged.

### Reuse, not a parallel code path

Clef reuses the machinery this repository already had rather than forking it:

- `validate_answers` is called unchanged. Clef names its three question types `noul`, `choice` and `score`, exactly as the System One API this client already speaks, so there is no second answer contract to keep in step.
- The score legend index check is the **existing `validate_laya_answers` helper**, the same one the local Laya route uses. A Clef `score` outside `0..len(criteria)-1`, or a `legend` contradicting the levels it was asked about, is rejected by the same rule.
- `_request_once` grew one optional `unwrap` parameter, which is the single place the routes differ. Clef passes its envelope reader and therefore reuses **the same three-attempt retry loop, the same header construction and the same error text** as OpenRouter and TypeSafe, instead of carrying a second copy of the loop.

## Changed

### One retry-loop detail, and one test

Two changes outside the Clef code, both needed to keep the additive promise:

- **`_request_once` now re-raises `JevSchemaError` as itself** instead of re-wrapping it in a plain `JevClientError`. A typed answer outside the contract was already never retried; it now also keeps its own type, so a caller can still tell a schema failure from a transport failure. No existing test depended on the old re-wrapping.
- **`test_no_hosted_mode_selects_the_local_route_on_its_own` no longer enumerates provider orders.** It asserted membership in a four-tuple allowlist of orders, which a new hosted provider fails by construction. It now asserts the property that the test is actually about: a hosted mode's order is non-empty, excludes `laya`, and contains only hosted providers. `clef` was the reason, and the property form means the next hosted provider is covered without editing this test.

Everything else is untouched. All four existing hosted modes, the plain local mode, the four `laya_then_*` chains, and both pre-existing DOGA aliases keep their exact provider orders, required keys, `provider_routing` blocks and error text; a test asserts every one of those nine orders is unchanged.

### Documentation

`README.md`, `docs/reference.md`, `docs/integrations.md`, `docs/approvals.md`, `.env.example` and `THIRD_PARTY_NOTICES.md` describe the new provider, its checkpoint choice, its two credentials, its privacy boundary and its failure behaviour. `docs/reference.md` gains a section, [the Cloudflare Clef route](../reference.md#the-cloudflare-clef-route). `THIRD_PARTY_NOTICES.md` records that Clef's weights are Apache 2.0 licensed and served by Cloudflare, that no Clef code or weights ship here, and that the route needs a Cloudflare account and a Workers AI token.

## Privacy and failure behaviour

A `clef` review sends the bounded `state` and the questions to Cloudflare. That is egress in the same sense as any other hosted route, and redaction applies on the same terms. It is not the same as the local `laya` route, which sends nothing off the machine.

A Clef failure is an **unavailable review**. It escalates through the same conservative path as any provider failure; it never approves, never becomes a weaker answer, and never silently becomes a different classifier's answer. The `laya_then_*` consecutive-failure breaker does not apply here, because there is no fallback hop to suppress: the counter bounds local failures reaching a *hosted fallback*, and Clef has none.

Log hygiene matches the 0.6.1 guarantee. A Clef failure logs **only the provider name and the exception class**, never the reviewed state, never the exception message, and never the credential. A test drives a failing review of `aws s3 rm s3://private-bucket --recursive` with a token set and asserts the captured log contains `JevClientError` while containing neither the command, nor the bucket, nor the token, nor the underlying error text.

## What was verified, and what was not

**Live verification was not performed, and could not be.** This machine has no Cloudflare credential authorized for Workers AI: every candidate token returns HTTP 401 "Authentication error" from `api.cloudflare.com`. **No live Clef call was made, and no test in this repository claims one succeeded.** Every Clef test drives an injected transport or a captured socket and asserts the route, not a live answer.

What the 84 new tests actually establish:

| Behaviour | How it is proved |
|---|---|
| Clef alone contacts no Jev or Laya provider | the captured URL is asserted to be the Cloudflare one and to contain no `openrouter`, `typesafe` or `127.0.0.1` |
| `clef-flash` routing | endpoint path and body `model` both asserted from a captured request |
| Both response envelopes parse | two captured bodies, the bare output and the `success`/`result` envelope |
| Top-level `answers` wins over `result.answers` | a body carrying both with different values |
| `success: false` raises with Cloudflare's code | codes `7000`, `10000` and `10001` asserted in the message |
| Missing token or account fails before any network call | `urlopen` is replaced by a fixture that **fails the test if called**, and the variable name is asserted in the message |
| Unknown choice rejected | `"MAYBE"` against the question's own criteria |
| Out-of-range score rejected | `-0.1`, `2.4` and `7` against a three-level question |
| Mapped question ids round trip | `candidate:aaa` and `hook:pre_tool_call` are asserted present under their **original** names in the result |
| Credentials and state never reach the log | captured log asserted to contain the class and none of the command, bucket, token or error text |
| The retry loop is shared, not forked | a captured 503 is retried and succeeds; a captured 500 is attempted exactly three times; a captured 401 fails on the first attempt |
| Every pre-existing test still passes | the full suite, below |

What remains unverified, plainly:

1. **No live Clef answer has ever been observed by this repository.** The answer fixtures in `tests/test_clef_provider.py` are written from Cloudflare's documented answer shapes, not captured from a real response. A first live run should be checked against them before being relied on.
2. **Clef's judgement quality is unmeasured.** No benchmark was run against Clef. The 0.6.1 notes on the local checkpoint's calibration apply with even more force to an unmeasured hosted route: calibrate on your own labelled examples before trusting it for a consequential decision.
3. **The account-id format check is a guard, not a Cloudflare contract.** The 32 lowercase hex rule was chosen to make a URL-rewriting value impossible to pass. If Cloudflare ever issues account ids in another form, that check would need revisiting; it fails closed in the meantime.
4. **Pricing and availability are Cloudflare's.** Workers AI billing and rate limits are not something this repository can state, and no quota behaviour is tested.

- `plugin.yaml` and `pyproject.toml` both read 0.7.0.
