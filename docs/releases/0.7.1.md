# Jev Decisions 0.7.1

## Live enforcement hardening

Jev Decisions 0.7.1 is a focused hardening release for the live boundary introduced in 0.7.0. It does not adopt an application specific route selector, a desktop execution model, or a foreign provider stack, because those features overlap neither Hermes' plugin contract nor an actual supported use case here.

The design boundary was checked against the original author's decision architecture, which states:

> "Keel owns the options, state checks, and permissions. The selector returns a choice or abstains."
>
> Avidlive, `codejunkie99/keel`, `docs/decision-architecture.md`, reviewed at commit `5cef4569e7f850a0b85dc998cc64c64e944c80a0`.

That principle is used here as a review criterion, not as a claim about Jev Decisions' identity.

## Changes

* Live authorization now sends Jev a bounded action descriptor, not only an argument hash. Argument values remain out of the descriptor and out of receipts.
* Local risk facts derive external, reversible, destructive, and credential flags from conservative action shape checks. Irreversible and sensitive actions require human approval before provider authorization.
* Live answers for authorization, memory, and anomaly decisions are strictly validated. Missing answers, unknown choices, nonfinite probabilities, and out of range scores fail closed.
* An `ask` result now returns Hermes' human approval directive. A `deny`, provider error, malformed response, or unavailable decision remains blocked.
* Live enforcement disables legacy shadow provider observers by default. Set `JEV_SHADOW_OBSERVERS=1` only when the duplicate observer path is deliberately wanted.
* Read only classification no longer treats every `jev_*` name as safe. Sensitive file paths and output options do not bypass the live boundary.
* Post tool verification keeps its local result correlation in live mode while legacy remote review remains separately controlled.
* Tool call correlation accepts Hermes' `tool_call_id` as well as the older `invocation_id` spelling.
* Verification receipts now record `verified` or `unverified` rather than a null decision.
* The live pre tool path uses one provider attempt with an eight second request budget, staying below Hermes' fail closed hook deadline instead of retrying beyond it.
* Reference documentation now describes all nine tools and the live hook behavior.

## Explicit limits

This release does not claim that `gate_memory` intercepts Hermes' durable memory provider. It remains an explicit decision tool until Hermes exposes and the plugin wires a supported memory write hook.

This release does not claim that arbitrary tool calls have become candidate selection. The descriptor improves semantic context, but the host still owns execution and Hermes approval remains authoritative. A future candidate based action API would require a separate design and real host integration.

## Verification

The release gate requires the full Python test suite, focused live enforcement and supervision tests, bytecode compilation, diff whitespace checks, and packaging metadata validation. A GitHub push is appropriate only after those checks pass and the resulting tag and remote state are verified.
